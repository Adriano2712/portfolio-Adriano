## Problem

Knowing a website or API is down before a customer reports it, with history to understand what happened, without running an external queue just to schedule checks.

## Result

- Multi-user monitor with check history, incidents opened and closed automatically and a public status page per account.
- Dashboard, monitor detail and status page update on their own when a monitor changes state.
- Alerts via email, Telegram and webhook.
- JWT authentication, isolation between accounts and SSRF protection.
- Tests in three layers: pytest (API and worker), Vitest (interface) and Playwright (end to end).

## Architecture

<Diagram id="architecture" />

The worker is a separate process that runs the same code as the API. It picks due checks straight from Postgres with `SELECT … FOR UPDATE SKIP LOCKED`: several workers can run together without taking the same check, and there is no Redis or queue to operate.

## Technical decisions

**Scheduling in Postgres, no external queue (ADR 0003).** `SKIP LOCKED` spreads work across workers using the database that already exists. One less piece to deploy, monitor and back up.

**SSRF protection (ADR 0005).** A monitor points to a URL chosen by the user, so the server must not become a bridge into the internal network. Registration and the worker accept only http and https and reject private, loopback and link-local IPs, resolved at check time.

**Best-effort alerts (ADR 0008).** A failing channel does not block the others or the processing of checks.

**Real time with Postgres `LISTEN`/`NOTIFY` (ADR 0010).** When a monitor changes state, the worker announces it through the database itself and the API relays it to the browser over Server-Sent Events. Again, no Redis and no queue.

**Deployed on free tiers (ADR 0011).** Frontend on Vercel, API on Render and database on Supabase. Render's free tier has no background workers, so a flag runs the scheduler inside the API; `SKIP LOCKED` still guarantees no check runs twice, and splitting the worker out again needs no code change.

**JWT bearer (ADR 0006)** and **a public status page per account (ADR 0009)**, showing only monitors marked as public.

## What went wrong and known limits

**False "down" behind anti-bot protection.** The worker uses `httpx`, with no browser. A CDN that blocks by HTTP/TLS fingerprint can return 403 for a site that works in a browser. Instead of trying to work around it, I documented the fix: allowlist the worker's IP in the CDN.

**DNS rebinding is not closed yet.** SSRF protection resolves the IP at check time, but a domain can change IP between the check and the connection. It is recorded in the ADR as the next hardening step.

**A scheduler with no supervisor.** Inside the API, a failed round (the database briefly unavailable, for example) would have silently killed the check loop, since there is no longer a container to restart it. The loop now logs the error and retries on the next round, with a test covering that case.

**The free tier sleeps.** Render shuts the service down after a period without traffic, and checks stop with it. An external pinger calls `/health` periodically to keep it awake.
